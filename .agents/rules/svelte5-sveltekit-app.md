# Bun + SvelteKit 2 + Svelte 5 Stack — Authoritative Coding Guidelines

This stack is a compiled, server-first, runes-native full-stack setup: Bun as the runtime/package-manager/test-runner, SvelteKit 2 for routing and data, Svelte 5 runes for reactivity, TypeScript in `verbatimModuleSyntax` mode, UnoCSS (with `unocss-preset-shadcn`) for styling, shadcn-svelte + bits-ui for components, and Biome for lint/format. Optimize for: fine-grained reactivity via runes (not stores), server-only data boundaries (load functions and remote functions), copy-in components you own (not a black-box UI dependency), and compiler-checked types generated by SvelteKit (`./$types`).

The single biggest way agents write wrong-but-plausible code here is by importing habits from adjacent ecosystems: writing Svelte 4 (`export let`, `$:`, `on:click`, stores, slots, `createEventDispatcher`), writing React (`useState`, `useEffect`, `className`, context-as-state), or writing Tailwind (`tailwind.config.js` content globs, `@apply` habits) when this stack uses UnoCSS. Two more traps are specific to this stack: putting mutable module-level state in a server module (it leaks across requests/users), and assuming shadcn-svelte's CLI `init` works — with UnoCSS you configure it by hand. Everything below shows the current, idiomatic way once.

## Bun as runtime, package manager, and test runner

Bun is the default for install, scripts, and tests. Use `bun install` (writes `bun.lock`, the text lockfile), `bun add` / `bun add -d`, and `bunx` in place of npx.

```bash
# scaffold
bunx sv create my-app        # SvelteKit CLI
cd my-app
bun install

# dev / build / preview — Vite runs on Node by default; --bun forces the Bun runtime
bun --bun run dev
bun --bun run build
bun run preview

# type-check (Vite does NOT type-check)
bun run check                # runs svelte-check
```

Critical insight: the Vite dev server and build run on **Node** unless you pass `--bun`. Bun only truly runs your app when you start a `Bun.serve()` server (production) or force it with `--bun`. Do not assume Bun runtime APIs are available in dev unless you forced them.

`bunfig.toml` for a SvelteKit project:

```toml
[install]
# exact = true            # pin exact versions if you prefer
# registry = "https://registry.npmjs.org"

[test]
preload = ["./src/test/setup.ts"]   # test setup file
coverage = false
```

Bun runtime APIs you should reach for in server-only code (`+server.ts`, `hooks.server.ts`, `.remote.ts`, `$lib/server/*`), never in components:

```ts
// password hashing (argon2id by default) — use for auth
const hash = await Bun.password.hash(plaintext);
const ok = await Bun.password.verify(plaintext, hash);

// SQLite (bun:sqlite) — synchronous, fast, great for local/edge data
import { Database } from "bun:sqlite";
const db = new Database("app.db", { strict: true });
const row = db.query("SELECT * FROM user WHERE id = ?").get(userId);

// files
const text = await Bun.file("data.json").text();
```

Use `Bun.password`, `bun:sqlite`, and `Bun.SQL` (Postgres) — do not add `bcrypt`, `better-sqlite3`, or `pg` unless you have a concrete reason; the built-ins avoid native-module install pain. Bun 1.4 also ships native `Bun.cron()`, `Bun.Image`, and `Bun.markdown`, replacing `node-cron`, `sharp`, and `marked` respectively for server-side work.

### `bun test` vs Vitest — pick per layer

| Use | Tool | Why |
|---|---|---|
| Pure functions, server logic, `.svelte.ts` rune modules | `bun test` | Fast; Jest-compatible API; zero config |
| Svelte component rendering | Vitest + `vitest-browser-svelte` | Needs the Svelte Vite plugin + a real browser |
| End-to-end | Playwright | Full navigation, forms, auth flows |

`bun test` uses a Jest-style API with `bun:test` imports:

```ts
import { describe, expect, it, mock } from "bun:test";
import { slugify } from "$lib/slug";

describe("slugify", () => {
  it("lowercases and hyphenates", () => {
    expect(slugify("Hello World")).toBe("hello-world");
  });
});
```

`bun test` cannot render `.svelte` components (no Svelte compiler in its pipeline). For components, use Vitest Browser Mode (below).

## SvelteKit 2 — routing, load, and the server boundary

File-based routing lives under `src/routes`. The file-purpose map is the thing agents most need to get right:

| File | Runs on | Purpose |
|---|---|---|
| `+page.svelte` | client + SSR | The page component |
| `+page.ts` | client + server | Universal load (runs both places) |
| `+page.server.ts` | server only | Server load + form `actions`; DB/secrets safe here |
| `+layout.svelte` / `+layout.ts` / `+layout.server.ts` | as above | Shared UI + data for a subtree |
| `+server.ts` | server only | API endpoints (`GET`/`POST`/…) returning `Response` |
| `+error.svelte` | client + SSR | Error boundary UI for the subtree |
| `hooks.server.ts` | server only | `handle`, `handleFetch`, `handleError`, etc. |
| `src/lib/server/**` | server only | Enforced server-only modules |

Choose universal (`+page.ts`) load when the data is public and you want it to run on the client during navigation; choose server (`+page.server.ts`) load when it touches secrets, a database, or private env.

Server load with generated types:

```ts
// src/routes/blog/[slug]/+page.server.ts
import { error } from "@sveltejs/kit";
import type { PageServerLoad } from "./$types";
import * as db from "$lib/server/database";

export const load: PageServerLoad = async ({ params, locals }) => {
  const post = await db.getPost(params.slug);
  if (!post) error(404, "Not found");   // SvelteKit 2: call, do NOT `throw`
  return { post, user: locals.user };
};
```

```svelte
<!-- src/routes/blog/[slug]/+page.svelte -->
<script lang="ts">
  import type { PageProps } from "./$types";
  let { data }: PageProps = $props();   // data is fully typed from load
</script>

<h1>{data.post.title}</h1>
```

In SvelteKit 2 `error()`, `redirect()`, and `fail()` are **called, not thrown** — `error(404)` and `redirect(303, "/login")` end the function by themselves. `fail(400, {...})` returns typed validation failures from form actions.

Streaming: return promises from a server load and await them in the template inside a boundary — the page shells out immediately and streams the rest:

```ts
export const load: PageServerLoad = async () => {
  return { comments: db.getComments() };  // unawaited promise → streamed
};
```

### Hooks and per-request state

`hooks.server.ts` is where auth, request context, and fetch rewriting live:

```ts
// src/hooks.server.ts
import type { Handle } from "@sveltejs/kit";
import * as auth from "$lib/server/auth";

export const handle: Handle = async ({ event, resolve }) => {
  const token = event.cookies.get("session");
  event.locals.user = token ? await auth.resolveSession(token) : null;
  return resolve(event);
};
```

Type `locals` in `src/app.d.ts`:

```ts
// src/app.d.ts
declare global {
  namespace App {
    interface Locals { user: import("$lib/server/auth").User | null; }
    interface PageData {}
    interface Error { message: string; code?: string; }
    interface PageState {}
    interface Platform {}
  }
}
export {};
```

### The no-shared-server-state rule

Never store mutable request/user state at module scope in a server module — one server instance serves many users and the value leaks across requests:

```ts
// ❌ WRONG — shared across every request on the server
let currentUser: User | null = null;
export function setUser(u: User) { currentUser = u; }
```

Put request-scoped state on `event.locals` (set in `handle`), and read it in loads/actions. For client-side shared state, use a `.svelte.ts` rune module or context (below) — never a server module.

### Environment variables

Use the four `$env` modules; never read `process.env` directly:

```ts
import { DATABASE_URL } from "$env/static/private";      // build-time, server-only
import { PUBLIC_API_BASE } from "$env/static/public";    // build-time, client-safe
import { env } from "$env/dynamic/private";              // runtime, server-only
```

Private env modules can only be imported into server-only files; importing them into a component is a build error — that is the safety feature, not a bug to work around.

### Cookies and CSRF

Use `event.cookies` — it sets `httpOnly`, `secure`, `sameSite: "lax"`, `path: "/"` sensibly by default:

```ts
event.cookies.set("session", token, { path: "/", httpOnly: true, maxAge: 60 * 60 * 24 * 7 });
```

SvelteKit blocks cross-origin form POSTs by default (CSRF protection). Form actions and remote forms are protected; keep the `Origin` check on.

### Adapters and running on Bun

For production on Bun, prefer **`@sveltejs/adapter-node` run under the Bun runtime** (`bun ./build/index.js`) — it is the officially maintained adapter and Bun runs it well. Use `svelte-adapter-bun` only if you specifically need a native `Bun.serve` entry (e.g. Bun WebSockets); note it has lagged the official adapter and is not always current.

```js
// svelte.config.js
import adapter from "@sveltejs/adapter-node";
import { vitePreprocess } from "@sveltejs/vite-plugin-svelte";

export default {
  preprocess: vitePreprocess(),
  kit: {
    adapter: adapter(),
    experimental: { remoteFunctions: true }  // opt-in; see below
  },
  compilerOptions: { experimental: { async: true } }
};
```

```bash
bun --bun run build
bun ./build/index.js       # production server on Bun
```

## Remote functions (experimental, available since 2.27)

Remote functions give type-safe client↔server calls with no hand-written API layer. Per the official docs they are "a tool for type-safe communication between client and server… This feature is currently experimental, meaning it is likely to contain bugs and is subject to change without notice." They live in `.remote.ts` files, always run on the server, and come in four kinds: `query` (read), `form` (progressive-enhancement mutation), `command` (imperative mutation), `prerender` (build-time data). Opt in via the two flags shown above (`kit.experimental.remoteFunctions` + `compilerOptions.experimental.async`). Validate every argument with a Standard Schema library (Valibot/Zod) because each function is a public HTTP endpoint.

```ts
// src/routes/blog/data.remote.ts
import * as v from "valibot";
import { query, form } from "$app/server";
import { error } from "@sveltejs/kit";
import * as db from "$lib/server/database";

export const getPosts = query(async () => db.allPosts());

export const getPost = query(v.string(), async (slug) => {
  const post = await db.getPost(slug);
  if (!post) error(404, "Not found");
  return post;
});

export const createPost = form(
  v.object({ title: v.string(), body: v.string() }),
  async ({ title, body }) => {
    const post = await db.createPost({ title, body });
    return { success: true, id: post.id };
  }
);
```

```svelte
<!-- consume: await directly in the template, inside a boundary -->
<script lang="ts">
  import { getPosts, createPost } from "./data.remote";
</script>

<svelte:boundary>
  <ul>
    {#each await getPosts() as { slug, title }}
      <li><a href="/blog/{slug}">{title}</a></li>
    {/each}
  </ul>
  {#snippet pending()}<p>Loading…</p>{/snippet}
</svelte:boundary>

<form {...createPost}>
  <input name="title" /><textarea name="body"></textarea>
  <button>Publish</button>
</form>
```

`query.batch` solves the N+1 problem by grouping same-macrotask calls; `.refresh()` re-fetches a cached query (queries are deduped and cached while on the page, so `getPosts() === getPosts()`). Arguments and return values are serialized with `devalue`, so `Date`, `Map`, and `Set` survive the round-trip. A query also exposes `loading`/`error`/`current` properties as an alternative to `await`.

Because remote functions are experimental and "subject to change without notice," for critical production paths that must not break on a SvelteKit minor, prefer classic `+page.server.ts` load + form `actions`. Remote functions and traditional endpoints coexist, so adopt incrementally.

## Svelte 5 — runes, snippets, events

Runes are the reactivity model. Component-local state is `$state`, derivations are `$derived`, side effects are `$effect`, props are `$props`.

```svelte
<script lang="ts">
  let count = $state(0);
  let doubled = $derived(count * 2);
  let big = $derived.by(() => {           // multi-statement derivations
    let n = count;
    return n > 10 ? "large" : "small";
  });

  $effect(() => {
    document.title = `Count: ${count}`;    // runs after DOM update, auto-tracks count
  });
</script>

<button onclick={() => count++}>{count} → {doubled} ({big})</button>
```

Decision rule: if you are **producing a value**, use `$derived`; if you are **performing an action**, use `$effect`. If an `$effect` body ends by assigning another `$state`, you almost certainly wanted `$derived`.

Rune reference an agent should know:

- `$state.raw(x)` — non-deep reactivity for large immutable structures (replaced wholesale, not mutated).
- `$state.snapshot(x)` — a plain, non-proxied clone to hand to libraries that choke on proxies.
- `$derived` is **overridable**: since Svelte 5.25 you may reassign a (non-`const`) derived for optimistic UI, and it reverts on the next dependency change.
- `$effect.pre` — run before DOM updates (e.g. autoscroll with `tick()`).
- `$effect.root` — a manually-managed effect scope you dispose yourself.
- `$effect.pending()` — count of in-flight promises when using experimental `await`.
- `$props.id()` — a stable unique id for a component instance (great for `for`/`aria-*`).
- `untrack(() => ...)` — read reactive state without registering a dependency.
- `$inspect(x)` / `$inspect(x).with(...)` — dev-only reactive logging; `$inspect.trace()` traces what re-ran an effect.

### Props, bindable, typing

```svelte
<script lang="ts">
  import type { Snippet } from "svelte";

  interface Props {
    label: string;
    value?: number;
    children?: Snippet;
  }
  let { label, value = $bindable(0), children }: Props = $props();
</script>

<label>{label}<input type="number" bind:value /></label>
{@render children?.()}
```

`$bindable` opts a prop into two-way binding; parents use `bind:value`. Type props with a local `interface` and destructure `$props()` — never `export let`.

### Snippets replace slots

Slots, `createEventDispatcher`, and `svelte:component` are gone. Use snippets + `{@render}`, callback props for events, and dynamic components as plain values:

```svelte
<!-- Table.svelte -->
<script lang="ts" generics="T">
  import type { Snippet } from "svelte";
  let { rows, row }: { rows: T[]; row: Snippet<[T]> } = $props();
</script>

<table><tbody>
  {#each rows as item (item.id)}
    <tr>{@render row(item)}</tr>
  {/each}
</tbody></table>
```

```svelte
<Table rows={users}>
  {#snippet row(user)}
    <td>{user.name}</td>
  {/snippet}
</Table>
```

Events are attributes: `onclick`, `oninput`, `onsubmit` — not `on:click`. Pass callbacks as props (`onselect={...}`) instead of dispatching events. Dynamic components render directly: `<svelte:component this={C}>` is replaced by `{@const C = getComp()}<C />` or just `<Comp />` where `Comp` is a `$state`/`$derived` value. Always key `{#each}` blocks with a stable id (`(item.id)`) so DOM reconciliation is correct.

### Reactive state in `.svelte.ts` modules

For shared client state, export runes from a `.svelte.ts` module (the `.svelte.ts` extension enables rune compilation). Prefer a class or a getter/setter object so reactivity survives across imports:

```ts
// src/lib/state/cart.svelte.ts
class Cart {
  items = $state<CartItem[]>([]);
  get total() { return this.items.reduce((s, i) => s + i.price, 0); }
  add(item: CartItem) { this.items.push(item); }
}
export const cart = new Cart();
```

Do not export a bare reassignable `let count = $state(0)` and expect consumers to see updates on reassignment — export the container (class/object) and mutate its fields.

For SSR-safe per-user state, use context set during component init rather than a module singleton (a module singleton is shared across all SSR requests on the server):

```svelte
<!-- +layout.svelte -->
<script lang="ts">
  import { setContext } from "svelte";
  import { UserState } from "$lib/state/user.svelte";
  let { data, children } = $props();
  setContext("user", new UserState(data.user));
</script>
{@render children()}
```

### Attachments and boundaries

`{@attach}` (attachments) is the current replacement for element actions (`use:`) where you need DOM access tied to lifecycle:

```svelte
<script lang="ts">
  import type { Attachment } from "svelte/attachments";
  const autofocus: Attachment = (node) => { node.focus(); };
</script>
<input {@attach autofocus} />
```

`<svelte:boundary>` catches render/async errors in a subtree with `pending` and `failed` snippets. Combined with experimental `await`, you can `await` in the template, in `$derived`, and at the top of `<script>`. Per the Svelte docs: "As of Svelte 5.36, you can use the await keyword inside your components in three places where it was previously unavailable… This feature is currently experimental, and you must opt in by adding the experimental.async option." The docs also state "The experimental flag will be removed in Svelte 6" — until then, treat async-in-components as experimental and confine it to boundaries with a `pending` snippet.

### `$app/state`, not `$app/stores`

Read navigation/page state from `$app/state`. Per the SvelteKit docs: "SvelteKit makes three read-only state objects available via the $app/state module — page, navigating and updated. This module was added in 2.12. If you're using an earlier version of SvelteKit, use $app/stores instead."

```svelte
<script lang="ts">
  import { page, navigating } from "$app/state";
  const id = $derived(page.params.id);   // reactive, no `$` prefix
</script>
{#if navigating.to}<p>Loading…</p>{/if}
```

There is no `$` store-prefix — `page` is a reactive object; read `page.url`, `page.params`, `page.data` directly. Per the SvelteKit v2 migration guide, "$app/stores is deprecated and subject to be removed in SvelteKit 3" — do not use it in new code. Use `$app/navigation` (`goto`, `invalidate`, `invalidateAll`, `preloadData`) for programmatic navigation, and `pushState`/`replaceState` from `$app/navigation` for shallow routing (modal-as-URL patterns via `page.state`).

## TypeScript configuration

Extend the SvelteKit-generated config and keep bundler-mode module resolution:

```jsonc
// tsconfig.json
{
  "extends": "./.svelte-kit/tsconfig.json",
  "compilerOptions": {
    "strict": true,
    "moduleResolution": "bundler",
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "skipLibCheck": true,
    "allowJs": true,
    "checkJs": true,
    "esModuleInterop": true,
    "resolveJsonModule": true
  }
}
```

`verbatimModuleSyntax` forces `import type` for type-only imports — this matters for Svelte files, because a value import that is actually a type can break compilation. Type components and DOM props with `svelte`/`svelte/elements`:

```svelte
<script lang="ts">
  import type { HTMLButtonAttributes } from "svelte/elements";
  import type { Snippet } from "svelte";

  let { children, ...rest }: HTMLButtonAttributes & { children: Snippet } = $props();
</script>
<button {...rest}>{@render children()}</button>
```

Use `Component`, `ComponentProps`, and `Snippet` from `svelte` for typing; use `generics="T"` on `<script>` for generic components. Run `svelte-check` (`bun run check`) in CI — Biome and `tsc` do not type-check Svelte templates.

## UnoCSS + unocss-preset-shadcn

This stack uses **UnoCSS, not Tailwind**. Wire UnoCSS through the Vite plugin with the UnoCSS plugin placed **before** `sveltekit()` (order matters for HMR):

```ts
// vite.config.ts
import { sveltekit } from "@sveltejs/kit/vite";
import UnoCSS from "unocss/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [UnoCSS(), sveltekit()],
});
```

Import the virtual stylesheet once in the root layout. **Do not also import
`@unocss/reset/tailwind.css`** — `presetWind4` ships its own preflight aligned with Tailwind
v4, and importing the Wind3 reset on top of it double-resets:

```svelte
<!-- src/routes/+layout.svelte -->
<script lang="ts">
  import "virtual:uno.css";
  let { children } = $props();
</script>
{@render children()}
```

One consequence to know about, because nothing warns you: the Wind3 reset carried
`button, [role="button"] { cursor: pointer }` (with a companion `:disabled { cursor: default }`),
and the Tailwind v4 preflight does not. Dropping the reset silently reverts every button to the
default arrow cursor. Restore it in your global stylesheet:

```css
button:not(:disabled), [role="button"]:not(:disabled) { cursor: pointer; }
```

Use **`presetWind4`** — the current Tailwind-v4-compatible preset. `unocss-preset-shadcn` 1.0.1
targets `presetWind4` from its root export (the legacy Wind3 build is at
`unocss-preset-shadcn/v3`), so this is the pairing the preset itself expects. `uno.config.ts`:

```ts
// uno.config.ts
import { defineConfig, presetWind4, transformerDirectives, transformerVariantGroup } from "unocss";
import presetAnimations from "unocss-preset-animations";
import { presetShadcn } from "unocss-preset-shadcn";

export default defineConfig({
  presets: [
    presetWind4(),
    presetAnimations(),
    presetShadcn({ color: "neutral" }),   // shadcn CSS-variable theming
  ],
  theme: {
    // preset-shadcn declares its radius scale under `borderRadius`, a Wind3 key that
    // presetWind4 ignores — restate it under `radius` or `rounded-*` silently stops
    // tracking `--radius` and falls back to Wind4's own defaults.
    radius: {
      sm: "calc(var(--radius) - 4px)",
      md: "calc(var(--radius) - 2px)",
      lg: "var(--radius)",
      xl: "calc(var(--radius) + 4px)",
    },
    // presetWind4 reads `font`, not `fontFamily`, and each value must be a SINGLE STRING.
    // Under the old key the block is ignored and `--font-*` gets Wind4's default stack;
    // under the right key an array emits no `--font-*` variable at all.
    font: { mono: '"JetBrains Mono", Consolas, monospace' },
  },
  transformers: [transformerDirectives(), transformerVariantGroup()],
  // shadcn-svelte variants live in .ts files — UnoCSS must be told to scan them
  content: {
    pipeline: {
      include: [
        /\.(vue|svelte|[jt]sx|mdx?|astro|elm|php|phtml|html)($|\?)/,
        "(components|src)/**/*.{js,ts}",
      ],
    },
  },
});
```

The `content.pipeline.include` addition is **required**: without it shadcn-svelte components render unstyled because their class strings live in `.ts` variant files UnoCSS would not otherwise scan. Use `unocss-preset-animations`, not `tailwindcss-animate` (installing both causes duplicate animation rules). Note the preset-shadcn README documents `darkSelector` and `componentLibrary: "reka"` options — those are for SolidUI/Vue; for shadcn-svelte just pass `presetShadcn({ color })`, which uses the default `.dark` class selector. For CSS-variable HSL themes use space-separated values (`--background: 0 0% 100%;`), not comma-separated.

Use the standard Vite plugin (above) for app development. `@unocss/svelte-scoped` is a separate mode for component libraries shipped via `svelte-package` (it hashes classes into each component); do not reach for it in a normal app.

If you are moving an existing project from `presetWind3`, three Tailwind v4 renames change
rendering silently — the build stays green and only the pixels move:

| Wind3 | Wind4 equivalent | Why |
|---|---|---|
| `shadow-sm` | `shadow-xs` | v4 shifted the shadow scale; `shadow-sm` now means the old `shadow` |
| `backdrop-blur-sm` | `backdrop-blur-xs` | same shift; `-sm` is now 8px, not 4px |
| `outline-none` | `outline-hidden` | v3's `outline-none` emitted `outline: 2px solid transparent`, which is the only focus indicator in Windows High Contrast Mode. v4's `outline-none` emits `outline-style: none` and drops it — a WCAG 2.4.7 regression. `outline-hidden` restores the transparent outline, scoped to `@media (forced-colors: active)` |

`presetWind4` also emits colour utilities as `color-mix(… , transparent)` rather than
`oklch(var(--token) / A)`. That is equivalent alpha scaling in any browser that takes the
`oklab` branch, so preset-shadcn's CSS-variable theming works unchanged — verify against a
build rather than assuming either way.

Prefer shortcuts and the object-form `class` attribute over long conditional string concatenation:

```svelte
<script lang="ts">
  let active = $state(false);
</script>
<!-- object form: keys are classes, values are booleans -->
<div class={["btn", { "btn-active": active, "opacity-50": !active }]}>…</div>
```

## shadcn-svelte + bits-ui

shadcn-svelte is **not a dependency** — its CLI copies component source into your repo (`$lib/components/ui/*`), and you own and edit those files. Components are runes-native (`$props`, snippets, `onclick`) and built on bits-ui primitives.

With UnoCSS you must **not** run `bunx shadcn-svelte@latest init` — that path assumes Tailwind. The preset-shadcn README is explicit: do not run `init`. Instead configure by hand:

1. Install deps: `bun add -d @lucide/svelte tailwind-variants clsx tailwind-merge`
2. Add the `cn()` util at `src/lib/utils.ts`
3. Hand-write `components.json`
4. Keep an empty `tailwind.config.js` in the root so the CLI's `add` command is satisfied
5. Add components: `bunx shadcn-svelte@latest add button dialog`

```ts
// src/lib/utils.ts
import { type ClassValue, clsx } from "clsx";
import { twMerge } from "tailwind-merge";

export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs));
}
```

```jsonc
// components.json
{
  "$schema": "https://shadcn-svelte.com/schema.json",
  "style": "default",
  "tailwind": { "config": "tailwind.config.js", "css": "src/app.pcss", "baseColor": "neutral" },
  "aliases": { "components": "$lib/components", "utils": "$lib/utils" }
}
```

The `tailwind` block is only there to satisfy the CLI; you are not running Tailwind. `cn()` uses `tailwind-merge` — it de-dupes standard Tailwind-style utility names (which preset-shadcn emits) correctly, but it will not merge custom UnoCSS shortcut names, so keep conditional overrides to standard utilities. (shadcn-svelte 1.5.x's own defaults assume Tailwind v4's CSS-first `@theme`; when using UnoCSS you diverge from that here deliberately — reconcile the `components.json` `tailwind` field by hand.)

### bits-ui composition and the child snippet

bits-ui is the headless/accessible primitive layer. Its distinctive pattern is **render delegation** via the `child` snippet: instead of the component rendering its own element, you render yours and spread the merged `props`:

```svelte
<script lang="ts">
  import { Dialog } from "bits-ui";
  import { fly } from "svelte/transition";
</script>

<Dialog.Root>
  <Dialog.Trigger>
    {#snippet child({ props })}
      <button {...props} class="btn">Open</button>
    {/snippet}
  </Dialog.Trigger>

  <Dialog.Portal>
    <Dialog.Overlay class="fixed inset-0 bg-black/50" />
    <Dialog.Content forceMount>
      {#snippet child({ props, open })}
        {#if open}
          <div {...props} transition:fly={{ y: 8 }} class="fixed left-1/2 top-1/2 …">
            <Dialog.Title>Title</Dialog.Title>
            <Dialog.Description>Body</Dialog.Description>
          </div>
        {/if}
      {/snippet}
    </Dialog.Content>
  </Dialog.Portal>
</Dialog.Root>
```

Always spread `{...props}` onto your element inside `child`, and pass your own `id`/handlers/classes to the bits-ui component (not the inner element) so they get merged via `mergeProps`. For Svelte transitions on floating content, combine `forceMount` + `child` + `{#if open}`. Two-way state uses `bind:` (`bind:open`, `bind:value`). When typing wrapper components, use `WithElementRef` and `WithoutChildrenOrChild` helpers and spread `ref`:

```svelte
<script lang="ts">
  import { Dialog as DialogPrimitive, type WithoutChildrenOrChild } from "bits-ui";
  let { ref = $bindable(null), ...rest }: WithoutChildrenOrChild<DialogPrimitive.ContentProps> = $props();
</script>
```

bits-ui removed the old `.Indicator`/`.Label`/`builders`/`let:` APIs; use the `children`/`child` snippet props to read state (checked/selected/open) and render custom indicators. `Combobox`, `Select`, and `Command` are first-class components — do not reach for the discontinued `cmdk-sv` (replaced by bits-ui's `Command`).

## Forms and validation

Two idiomatic paths:

- **Remote `form`** (experimental) for new code that wants zero API glue (shown above).
- **Superforms 2 + form actions** for the mature, production-safe path with rich UX (tainted-field detection, focus management, nested data).

Superforms uses Standard Schema adapters — prefer **Valibot** (smaller client bundle) or Zod. Define schema and defaults at module top-level (the adapter is memoized by reference):

```ts
// src/routes/signup/+page.server.ts
import { superValidate, message } from "sveltekit-superforms";
import { valibot } from "sveltekit-superforms/adapters";
import * as v from "valibot";
import { fail } from "@sveltejs/kit";
import type { PageServerLoad, Actions } from "./$types";

const schema = v.object({
  email: v.pipe(v.string(), v.email()),
  password: v.pipe(v.string(), v.minLength(8)),
});

export const load: PageServerLoad = async () => ({ form: await superValidate(valibot(schema)) });

export const actions: Actions = {
  default: async ({ request }) => {
    const form = await superValidate(request, valibot(schema));
    if (!form.valid) return fail(400, { form });
    // …create user…
    return message(form, "Account created");
  },
};
```

```svelte
<!-- +page.svelte -->
<script lang="ts">
  import { superForm } from "sveltekit-superforms";
  import type { PageProps } from "./$types";
  let { data }: PageProps = $props();
  const { form, errors, enhance, submitting } = superForm(data.form);
</script>

<form method="POST" use:enhance>
  <input name="email" type="email" bind:value={$form.email} />
  {#if $errors.email}<span>{$errors.email}</span>{/if}
  <input name="password" type="password" bind:value={$form.password} />
  <button disabled={$submitting}>Sign up</button>
</form>
```

For plain (non-Superforms) actions, use `use:enhance` from `$app/forms` for progressive enhancement; the form still works without JS.

## Auth pattern

Sessions via hooks + cookies + `Bun.password`, resolved into `locals`:

```ts
// src/lib/server/auth.ts
import { Database } from "bun:sqlite";
const db = new Database("app.db", { strict: true });

export async function verifyLogin(email: string, password: string) {
  const user = db.query("SELECT * FROM user WHERE email = ?").get(email) as any;
  if (!user || !(await Bun.password.verify(password, user.password_hash))) return null;
  return user;
}
```

```ts
// login action
import { redirect, fail } from "@sveltejs/kit";
export const actions = {
  default: async ({ request, cookies }) => {
    const data = await request.formData();
    const user = await verifyLogin(String(data.get("email")), String(data.get("password")));
    if (!user) return fail(401, { error: "Invalid credentials" });
    const token = await createSession(user.id);
    cookies.set("session", token, { path: "/", httpOnly: true, sameSite: "lax", maxAge: 604800 });
    redirect(303, "/dashboard");
  },
};
```

Guard routes in server loads by checking `locals.user` and calling `redirect(303, "/login")`.

## Biome — lint and format

Biome is the formatter and JS/TS linter. Critical limitation: `.svelte` template support is **experimental** — Biome fully handles `<script>` (JS/TS) and `<style>` (CSS), and since v2.3 can parse Svelte files under an opt-in flag (with control-flow syntax like `{#if}` improved through v2.4/2.5), but it is not a substitute for Svelte-aware template checking. Run `svelte-check` for template/type correctness alongside Biome.

```jsonc
// biome.json
{
  "$schema": "https://biomejs.dev/schemas/2.4.0/schema.json",
  "formatter": { "enabled": true, "indentStyle": "space", "indentWidth": 2, "lineWidth": 100 },
  "linter": { "enabled": true, "rules": { "recommended": true } },
  "javascript": { "formatter": { "quoteStyle": "double", "semicolons": "always" } },
  "files": { "includes": ["src/**", "*.ts", "*.js"] }
}
```

```bash
bunx biome check --write        # lint + format + safe fixes
bunx biome ci                   # CI mode (no writes, non-zero on issues)
```

To enable experimental Svelte parsing, opt in with `"html": { "experimentalFullSupportEnabled": true }` — but keep `svelte-check` as the authority for template correctness regardless.

## Anti-patterns to avoid

| ❌ Wrong (adjacent-ecosystem habit) | ✅ Right (this stack) |
|---|---|
| `export let value;` | `let { value } = $props();` |
| `$: doubled = count * 2;` | `let doubled = $derived(count * 2);` |
| `on:click={fn}` | `onclick={fn}` |
| `createEventDispatcher()` + `dispatch("x")` | callback prop: `let { onx } = $props()` then `onx?.()` |
| `<slot />` / `<slot name="x">` | `{@render children()}` / named snippets |
| `import { page } from "$app/stores"; $page.url` | `import { page } from "$app/state"; page.url` |
| `throw error(404)` / `throw redirect(303, …)` | `error(404)` / `redirect(303, …)` (call, no `throw`) |
| Mutable module-scope state in a server file | `event.locals` (server) / context or `.svelte.ts` (client) |
| `bcrypt` / `better-sqlite3` / `pg` | `Bun.password` / `bun:sqlite` / `Bun.SQL` |
| conditional class string concatenation | object-form `class={["btn", { active }]}` |
| `bunx shadcn-svelte init` (with UnoCSS) | hand-write `components.json`; `add` only; empty `tailwind.config.js` |
| `tailwindcss-animate` | `unocss-preset-animations` |
| `lucide-svelte` | `@lucide/svelte` (the scoped package is the maintained line; the unscoped one is Svelte 4 source) |
| `presetWind3` / `presetUno` | `presetWind4` (Tailwind v4-compatible; what preset-shadcn 1.0.1 targets) |
| `cmdk-sv` command palette | bits-ui `Command` |
| `svelte:component this={C}` | `<C />` where `C` is a reactive value |
| `use:action` for new DOM lifecycle logic | `{@attach fn}` attachments |
| Relying on Biome to lint `.svelte` templates | `svelte-check` for template/type correctness |
| Trusting remote-function args unvalidated | validate with Valibot/Zod (public endpoints) |
| `process.env.X` | `$env/static/*` or `$env/dynamic/*` modules |
